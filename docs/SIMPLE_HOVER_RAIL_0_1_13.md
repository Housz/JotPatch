# JotPatch 0.1.13 — Simple Hover Rail / 简洁直达导航

## 用户反馈与根因

在 v0.1.12 中，密集区域的彩色便签或灰色 Prompt 按钮调用 `needsRailDetail` 拦截本来的 `click`，自动打开标题为“附近 x 个导航目标”的二级列表。它增加了非必要的第二步选择，还让用户不知道原来悬停的那个标记对应列表中的哪一项。Prompt 与便签提示又分别显示轮次和锚定状态标题，重复占据空间。

## 实现方案

- **从源头移除二级选择**：没有 `#jp-rail-detail` DOM、选择弹窗 CSS、拥挤弹窗延迟和鼠标捕获、按钮 `needsRailDetail` 拦截；也不将空白轨道点击解释为“选择附近目标”。
- **所有轨道按钮只负责直接跳转**：灰条 `jumpToTurn(turn)`，彩色便签 `goTo(note.id)`，键盘 Enter/Space 保持原生 Button 行为。
- **统一内容摘要**：Prompt 与便签共用纯文本 `showRailPreview`。无独立的“已发现第 X 轮”“原文已关联”等标题/状态行；仅在 `aria-label` 中保留辅助信息供读屏使用。
- **极密区域的真实命中修复**：不再有列表帮助解开重叠，因此运行真实浏览器命中测试，发现原版典型 100 轮、60 便签中 **20/60** 按钮中心可物理点击。新增 `railNoteLanes`：在中心纵向距离不足 7px 时，以最多 3 条窄水平轨道分别放置相邻按钮，**不改变纵向坐标或上下顺序**；上述场景变为 **60/60** 按钮中心可物理点击，灰条也为 100/100。
- **颜色与数据兼容**：不增加网站权限，不改变 `Note.schemaVersion:1`、存储键、已有锚点、Markdown 与 Unpin 行为。原文虚拟化丢失时继续保留原色和虚线边框，不会自动打开便签。

## 测试

`npm run check`、`npm run test:e2e`。

特别覆盖 640px/850px 两种窗口高度下，100 轮、60 张笔记，鼠标在三个横向通道各点击一次，分别打开对应文本；灰色 Prompt 横条实际鼠标点击；所有悬停摘要无标题；稀疏笔记原有点击；10/50/90% 位置及 5/7/9% 相对比例；虚拟化保护、编辑与数据恢复。

测试基于合成网页与模拟存储。登录态 ChatGPT/Gemini 的真实 DOM 变化和 Chrome/Edge MV3 生命周期仍需要用户设备上验收。超过三张便签在几乎同一像素高度时，个别目标仍可能无法通过直接鼠标准确命中；顶部完整目录与键盘交互保留为**用户主动使用**的备用方式，不再自动弹窗。
