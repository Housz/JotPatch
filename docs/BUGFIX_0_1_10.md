# JotPatch v0.1.10 — Real Multicolor Overview + Hover Lens

## 根因（经 v0.1.9 实际源码确认）

1. 原 `layoutConversationRail().dense` 仅由 `Σ(14 + 15 × 该轮便签数) > 轨道可用高度` 决定。低轮次但同轮大量便签可能不触发全局密集门控。
2. **最关键：即使 `dense=true`，`renderDock()` 仍然为每张便签插入一个 `.rail-pin`；不存在任何概览短段的 DOM/CSS。** 因此旧版不会出现设计中的“多色微段概览”，观察到很多黄色点是符合旧代码的行为，但不符合产品设计。
3. `showNotePreview()` 在 `dense=true` 时直接返回；便签自己的 `pointerenter` 不保证直接打开 lens。用户只在某些很窄的轨道区域内移动鼠标才可能触发。
4. 当 ChatGPT 动态挂载的轮次少于 3 时，代码进入便签专用分支，完全不构建 Rail Layout，也就不可能出现密集展开。这解释了长会话当前仅挂载少数轮次时的实际体验差异。

## v0.1.10 设计与实现

- **真实概览态**：同轮至少 4 张便签就渲染 `.rail-overview`，内部包含最多六段真实便签颜色，颜色相同时仍有条间隔；其余便签在布局容许时独立可点击。对于 2–3 张密集到没有足够点击间距的场景也可压缩。
- **悬停局部展开**：概览按钮和其轨道区域都可以打开展开层。展开层保持原来的正文预览、颜色、精确锚定跳转；不需要点击数字胶囊。与 v0.1.9 一样，概览坐标不因鼠标移动而重排。
- **跨轮高密度概览**：如果 30 张便签分散在 60 轮、每轮只有一张，但轨道每张能分到的高度不足 28px，按稳定的屏幕位置窗口将相邻便签组成概览；灰色 Prompt 横条仍保持原位。
- **低轮次/普通网页降级**：当 `showTurns=false` 时，将便签按文本相对位置分组；当该位置出现至少 4 张，或者整体很密集导致每格有 ≥2 张时，渲染相同的色段概览/悬停展开。否则直接保留独立彩色点。
- **不改变存储 schema / 权限 / 私有 API 使用策略**。仍保留原文缺失时的颜色与虚线边框策略、动态虚拟化防误弹策略及原有 Markdown 编辑器。

## 明确的测试入口

- `npm run check`：18 项 TypeScript/契约/布局测试。
- `python tests/overview_e2e.py`：真实鼠标操作（640 / 850 / 1080 高度），12 轮 + 4 张便签、全黄色 7 张、只挂载 2 轮但有 24 张、普通网页 30 张、60 轮中分散 30 张，检查真正的色段 DOM、hover 稳定性、一键选择和没有页面 JS 异常。
- `npm run test:e2e`：以上新用例与所有早期的锚定、虚拟化、WYSIWYG、Gemini、拖动、保存测试。

注意：浏览器模拟测试运行在无真实登录态的合成 HTML 上。ChatGPT/Gemini 站点的 DOM 可能随时间变化，真实安装后仍需验收。

## 触发边界

- 对话轮次可识别：同一轮 **≥4 张**直接出现多色微条概览，不需要等全场对话到 100 轮；2–3 张只有确实空间拥挤时才压缩。
- 对话轮次无法识别、普通文章：密集导航通过网页相对位置分组；只要一个区域内多个便签足够拥挤，就可以看到色段概览。
- 若几十张便签分散到不同轮次，**轨道空间不够**时也会合并相邻的彩色点；如果每张仍有足够空间，保留独立彩色点用于一键访问。
